ZUSTAND (REACT)

import { create } from 'zustand';

export const useCartStore = create((set) => ({
  items: [],
  add: (product) => set((s) => ({ items: [...s.items, product] })),
  clear: () => set({ items: [] }),
}));

// компоненти — без Provider
function CartBadge() {
  const count = useCartStore((s) => s.items.length); // селектор
  return <span className="badge">{count}</span>;
}

function ProductCard({ product }) {
  const add = useCartStore((s) => s.add); // не ререндериться при зміні items
  return <button onClick={() => add(product)}>Купити</button>;
}

PINIA (VUE)

// stores/cart.js
import { defineStore } from 'pinia';
import { ref, computed } from 'vue';

export const useCartStore =
  defineStore('cart', () => {
  const items = ref([]);
  const count = computed(
    () => items.value.length
  );

  function add(product) {
    items.value.push(product); // просто мутуємо
  }

  return { items, count, add };
});

import { useCartStore } from '@/stores/cart';

import { makeAutoObservable } from 'mobx';

class CartStore {
  items = [];

АТОМАРНИЙ ПІДХІД: JOTAI

Як useState, але спільний

import { atom, useAtomValue, useSetAtom } from 'jotai';

const itemsAtom = atom([]);
const countAtom = atom((get) => get(itemsAtom).length); // похідний
const addAtom = atom(null, (get, set, product) =>
  set(itemsAtom, [...get(itemsAtom), product]));       // лише запис

function CartBadge() {
  return <span className="badge">{useAtomValue(countAtom)}</span>;
}

function ProductCard({ product }) {
  const add = useSetAtom(addAtom);
  return <button onClick={() => add(product)}>Купити</button>;
}
  • Замість одного великого store — дрібні атоми (bottom-up)
  • Компонент підписується на конкретний атом

СИГНАЛИ

Реактивність на рівні значення, а не компонента

  • Сигнал = значення + список тих, хто його читає
  • Читання → автоматична підписка
  • Зміна → оновлюються лише залежні обчислення і шматки DOM
  • Fine-grained reactivity
React:
  setState → ререндер компонента
           → ререндер дітей
           → порівняння Virtual DOM
           → оновлення DOM

Сигнали:
  count.value++ → оновлення
                  одного текстового
                  вузла в DOM

Тренд останніх років: Vue, Solid, Svelte 5, Preact, Qwik

СИГНАЛИ: ТРИ ПРИМІТИВИ

import { signal, computed, effect } from '@preact/signals';

const items = signal([]);
const count = computed(() => items.value.length);

effect(() => {
  document.title = `Кошик (${count.value})`; // перезапуститься при зміні count
});

items.value = [...items.value, product]; // → оновляться count і effect
ПримітивЩо робить
signalЗберігає значення, повідомляє про зміни
computedПохідне значення, кешується, перераховується лише за потреби
effectПобічна дія, перезапускається при зміні залежностей

  • React свідомо не має сигналів: модель «ререндер + Virtual DOM»

  • Сигнали можна підключити (@preact/signals-react), але це йде проти моделі React
  • TC39 Signals — пропозиція додати сигнали в сам JavaScript (рання стадія)

ЩО ОБРАТИ?

  • Тема, мова, користувач → Context
  • Кошик, фільтри в середньому застосунку → Zustand (React) / Pinia (Vue)
  • Великий застосунок, команда, складні потоки даних → Redux Toolkit
  • Багато дрібних незалежних шматків стану → Jotai
  • Дані з сервера → не в store: TanStack Query, RTK Query, loader

Головне — не тягнути весь стан у глобальне сховище

ЯКУ ПРОБЛЕМУ ВИРІШУЄ REDUX?

КОЛИ ВИКОРИСТОВУВАТИ REDUX?

✓ Варто використовувати

  • Складна логіка стану
  • Багато компонентів використовують один стан
  • Потреба в передбачуваності
  • Часті оновлення стану
  • Велика команда розробників
  • Потреба в time-travel debugging

✗ НЕ варто використовувати

  • Малий проєкт (до 10 компонентів)
  • Простий локальний стан
  • Стан використовується в 1-2 компонентах
  • Прототипування/MVP
  • Статичні дані

REDUX

  • Автор – Ден Абрамов
  • Бібліотека для організації архітектури застосунку
  • Однонаправлений потік даних
  • Іммутабельний стан

FLUX АРХІТЕКТУРА

REDUX

STATE. СТАН.

Місце, де зберігається весь стан застосунку.

ACTION. ДІЯ.

  • Стан неможливо змінювати напряму
  • Стан необхідно змінювати через дію
  • Те, "як" ми змінюємо дані

DISPATCH. ДІСПЕТЧЕР.

  • Звертаємось до діспетчера
  • Передаємо дію
  • Той, "хто" ми змінюємо дані

REDUCER. РЕДЮСЕР.

  • Система, через яку проходить взаємодія
  • Знаходиться вся логіка
  • Там, "де" працюють з даними

STORE

createStore і Provider

import { createStore } from 'redux';
import { Provider } from 'react-redux';

const defaultState = {
  counter: 0
}

const counterReducer = (state = defaultState, action) => {
  switch (action.type) {
    case "INCREASE_COUNTER":
      return {...state, counter: state.counter + Number(action.payload)};
    case "DECREASE_COUNTER":
      return {...state, counter: state.counter - Number(action.payload)};
    default:
      return state;
  }
}

const store = createStore(counterReducer);

root.render(
  <React.StrictMode>
    <Provider store={store}>
      <App />
    </Provider>
  </React.StrictMode>
);

BEST PRACTICES

  • Нормалізація даних - зберігайте дані в плоскому вигляді, як в БД
  • Використовуйте селектори - створюйте функції для вибірки даних
  • Мемоізація - використовуйте reselect для оптимізації
  • Не зберігайте все в Redux - локальний UI стан залишайте в компонентах
  • Іменування actions - використовуйте формат "domain/eventName"
  • Redux Toolkit - використовуйте RTK замість plain Redux

MIDDLEWARE

Проміжний шар між dispatch і reducer

  • Перехоплює actions перед тим, як вони потраплять до reducer
  • Може змінювати, затримувати, або блокувати actions
  • Використовується для async логіки, логування, аналітики
  • Middleware викликаються в ланцюжку

ЯК ПРАЦЮЄ MIDDLEWARE

ВЛАСНИЙ MIDDLEWARE (LOGGER)

const loggerMiddleware = (store) => (next) => (action) => {
  console.log('Dispatching:', action);
  console.log('State before:', store.getState());

  const result = next(action);

  console.log('State after:', store.getState());
  return result;
};

const store = createStore(
  rootReducer,
  applyMiddleware(loggerMiddleware)
);
